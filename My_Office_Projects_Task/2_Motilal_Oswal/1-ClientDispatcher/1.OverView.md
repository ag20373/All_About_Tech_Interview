# Client Dispatcher (CD) – Interview Preparation Notes

> **Source:** Notes transcribed and organized from the uploaded `Interview_QA.md` screenshots. A few screenshots are motion-blurred; unclear details are marked rather than guessed.

## 1. Two-minute introduction

**Q1. Tell me about the Client Dispatcher in your system.**

The Client Dispatcher (CD) is the front gate of the trading platform. Every trading terminal—desktop TWS, mobile app, or third-party API client—connects only to the CD. A terminal never talks directly to the Login Server, Risk Server, Report Server, or Exchange.

The CD contains very little business logic. It receives a message, validates it, decides where it should go, forwards it, and brings the reply back to the correct terminal.

There are three main flows:

- **Login/password:** routed to the Login Server.
- **Orders:** sent first to the Risk Validator for margin and risk checks. The approved order returns to the CD, which routes it to the correct exchange adapter (for example NSE, BSE, F&O, or currency).
- **Reports:** requests such as positions, order downloads, and trade downloads go to the Report Server.

The CD is built in C#. It uses a TCP server for terminals, queues, and separate thread pools for login, orders, reports, and mapping. This isolation ensures a slow report cannot delay order confirmations.

**Easy way to remember:** CD is the main gate. Terminals talk to the CD; the CD mainly routes messages.

## 2. Architecture and startup

### Q2. Which components does the CD talk to?

There are four kinds of components:

1. Login Server
2. Report Server
3. Risk Validator
4. Exchange adapters, called **Unifiers**

Components are discovered through **multicast**. When a component announces itself, the CD connects to it.

- Login and Report connect automatically.
- Exchange adapters and Risk connect automatically only when their `IsAutoConnect` flags are enabled.
- Otherwise, an operator clicks **Connect All** in the CD window.

### Q3. What happens when the CD starts?

1. Reads `Dispatcher.xml` for its `ComponentId`, listener IP and port, and multicast settings.
2. Checks that another CD instance is not already running from the same folder.
3. Starts the network shell and TCP terminal listener.
4. Starts the Login, Report, Risk, and Exchange handlers.
5. Starts a small sender that copies exchange replies to the Risk Server.

### Q4. How does the CD identify a client or terminal?

Every packet has a fixed header containing:

- Message code
- Message length
- Error code
- Client or terminal ID
- Client Dispatcher ID

The CD maintains a dictionary called `TerminalCollection`, keyed by terminal ID. For each terminal, it stores the live socket, logged-in flag, and counters for messages received, sent, and failed.

## 4. Login flow and session state

### Q7. What extra things happen during login?

The CD:

- Checks the version number.
- Optionally allows older versions using `AllowPreviousVersion` and `PreviousVersionNo`.
- Checks that **Accept Login** is switched on.
- Stamps its own `ComponentId` into the header so the reply knows which CD to return to.
- Adds the terminal's real IP address.
- Forwards the request to the Login Server.

### Q8. How does the login state work?

Each terminal has two connection slots:

- `RequestedConnectionContext`: the connection asking to log in.
- `ConnectionContext`: the officially logged-in connection.

When the Login Server replies successfully, the CD moves the requested connection into the logged-in slot and sends the reply.

If login fails, the CD sends the error and clears the requested slot. This prevents one connection from using another connection's session.

## 5. Order flow — most important

### Q9. Explain the life of an order.

1. A terminal sends an order to the CD.
2. The CD checks that the user is logged in.
3. The CD sends the order to the Risk Validator.
4. Risk performs margin and risk checks and returns the approved order to the CD.
5. The CD checks the exchange code and selects the matching exchange adapter. Examples include NSE cash, BSE cash, NSE F&O, BSE F&O, currency, MCX, and NCDEX.
6. For modify and cancel requests, the CD uses the exchange dispatcher ID stored in the order. This sends the request to the same adapter instance that handled the original order.
7. The exchange sends confirmations, rejects, and trade confirmations.
8. The CD forwards each reply to the terminal.
9. The CD also sends a copy to the Risk Validator, with the CD ID stamped in, so Risk can update positions and margin.

**Flow to memorize:**

`Terminal → CD → Risk → CD → Exchange Adapter → CD → Terminal`

The exchange reply is also copied from the CD to Risk.

### Q10. Why does the reply go to Risk as well?

Risk needs the actual order state—what was confirmed, rejected, or traded—because margin and positions depend on it. Therefore, confirmations, rejects, trade confirmations, and stop-loss triggers are also copied to the Risk Validator.

### Q11. What happens if the exchange adapter is not connected?

The CD converts the order into a reject with error code `AdapterNotConnected` and returns it to the terminal.

## 6. Dispatching and performance

### Q12. How does the CD send replies back efficiently?

The visible screenshot indicates that outgoing packets are tagged with a packet type, such as Login, OrderTrade, Report, or MappedConfirmation. Each packet type has its own sender pool/thread handling, keeping different traffic types isolated.

The scheduler follows two visible rules:

- Packets for the **same client and same message type** are kept on the same thread, preserving order.
- For a **new/different client**, work is assigned using the shortest queue, helping distribute load.

### Q13. How do you make sure replies are not out of order?

The visible answer says that a client is pinned to one processing thread while it has pending messages. Each client has message counters/sequencing for packet types. ## 7. Monitoring

### Q18. How do you monitor the CD?

The CD has a window showing:

- Connected components
- Queue sizes
- Number of terminals

It can toggle **Accept Login**, edit settings, and connect components.

It also pushes connected and total terminal counts to the NTS dashboard on a timer. A **LogReader** tool connects to the CD to request margin summaries and log out clients.

## 8. Design and scalability questions

### Q19. Why have a CD at all? Why not let terminals talk to the servers?

The CD provides a **single entry point**. It centralizes:

- Login-state checks
- Message validation
- Version control
- Encryption
- Load handling and monitoring

It hides internal servers from clients and allows backend servers to be restarted or replaced without changing the terminals.

### Q20. Why separate queues and pools by packet type?

This provides **isolation**. Order and trade traffic is latency-sensitive, while reports can be large and slow. Separate queues and pools prevent a slow report from starving or delaying order confirmations.

## 9. Last-minute cheat sheet

- **CD:** single front gate for all terminals.
- **Components:** Login, Report, Risk Validator, Exchange Adapters/Unifiers; discovered by multicast.
- **Incoming path:** TCP → decrypt → common queue → worker pool → checks → route by message code.
- **Checks:** terminal ID, logged-in state, same connection, message size (API), and header fields.
- **Order path:** Terminal → CD → Risk → CD → Exchange Adapter (by `ExchangeCode`) → CD → Terminal; exchange replies are copied to Risk.
- **Modify/cancel:** route to the same adapter using `ExchangeDispatcherID`.
- **Packet types:** Login, OrderTrade, Report, MappedConfirmation; separate sender pools.
- **Ordering/load balancing:** same client/type stays on the same thread; new client uses the shortest queue.
- **Errors returned to terminal:** `LoginServerNotAvailable`, `ReportServerNotAvailable`, `ComponentError`, `AdapterNotConnected`, `UserNotLoggedIn`.
- **Variants:** Normal, Mobile, Open API.
- **Configuration:** `Dispatcher.xml`.
