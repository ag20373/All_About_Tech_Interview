## Easy Interview Explanation, Algorithm and Client Dispatcher Example

> **Interview goal:** Be able to explain how to build a basic TCP client-server application from scratch, then explain how the same idea is used in the Client Dispatcher (CD) project.
>
> Start with the basic client/server concept. Do not begin with trading-specific classes, queues or login-session details unless the interviewer asks for them.

# 1. Understand the basic architecture

A TCP application has two sides:

- **TCP Server:** waits for clients to connect, accepts connections, receives messages and sends responses.
- **TCP Client:** connects to the server, sends messages and receives responses.

```text
       TCP CLIENT                         TCP SERVER
  +------------------+              +----------------------+
  | Desktop App      |              |                      |
  | Mobile App       | -- TCP ----> |  Server IP + Port    |
  | API Client       | <--- TCP --- |  Listener             |
  +------------------+              |                      |
                                    |  Accept connection   |
                                    |  Receive message      |
                                    |  Process message      |
                                    |  Send response       |
                                    +----------------------+
```

The client needs the server's IP address and port number to connect.

- **IP address:** identifies the machine/network endpoint.
- **Port:** identifies the application endpoint on that machine.
- **Socket:** the communication endpoint used by the application.
- **TCP:** provides a reliable, ordered, two-way byte stream.

# 2. Easy algorithm to remember

Think of the application as two separate algorithms.

## A. TCP Server algorithm

**In simple words:** Start the server, wait for a client, accept it, receive a message, process it and send a response.

```text
START SERVER
     |
     v
Create TCP Listener
     |
     v
Set Server IP Address and Port
     |
     v
Start Listening
     |
     v
Wait for Client
     |
     v
Accept Client Connection
     |
     v
Get Client Socket / Connection
     |
     v
Receive Client Data
     |
     v
Process the Data
     |
     v
Send Response to Client
     |
     v
Wait for Next Message
     |
     v
Client Disconnected?
     |
     +---- NO ----> Receive Next Message
     |
     +---- YES ---> Close / Clean Up Connection
```

## B. TCP Client algorithm

**In simple words:** Create a client, connect to the server, send a message, receive the response and close the connection when finished.

```text
START CLIENT
     |
     v
Create TCP Client
     |
     v
Enter Server IP Address and Port
     |
     v
Connect to Server
     |
     v
Connection Successful?
     |
     +---- NO ----> Handle Connection Error
     |
     +---- YES
           |
           v
       Send Message
           |
           v
       Receive Response
           |
           v
       Display / Process Response
           |
           v
       Need to Send Another Message?
           |
           +---- YES ---> Send Next Message
           |
           +---- NO ----> Close Connection
```

# 3. Step-by-step explanation for an interview

### Step 1: Create the server

The server creates a TCP listener. It chooses an IP address and port on which it will accept connections.

### Step 2: Start listening

The server starts listening for incoming client connection requests.

### Step 3: Client connects

The client creates a TCP connection using the server's IP address and port.

### Step 4: Server accepts the connection

The server accepts the connection. It now has a socket/connection through which it can communicate with that client.

### Step 5: Client sends data

The client sends a message through the TCP connection.

### Step 6: Server receives and processes data

The server reads the received bytes, interprets the message according to the application's protocol and processes it.

### Step 7: Server sends a response

The server sends the response through the same client connection.

### Step 8: Continue or disconnect

The client and server can exchange more messages while the connection remains open. When either side closes the connection, the other side detects it and cleans up its connection resources.

# 4. Generic C# example — simple TCP server

This is a learning example. It uses newline-terminated text messages so the receiver knows where one message ends. It is not the binary packet protocol used by the trading project.

```csharp
using System;
using System.IO;
using System.Net;
using System.Net.Sockets;

class TcpServer
{
    static void Main()
    {
        // 1. Create TCP listener
        TcpListener server =
            new TcpListener(IPAddress.Any, 5000);

        // 2. Start listening
        server.Start();

        Console.WriteLine("Server started...");

        // 3. Wait for a client
        while (true)
        {
            TcpClient client = server.AcceptTcpClient();

            Console.WriteLine("Client connected!");

            // 4. Handle this client
            using (client)
            using (NetworkStream stream = client.GetStream())
            using (StreamReader reader = new StreamReader(stream))
            using (StreamWriter writer = new StreamWriter(stream)
            {
                AutoFlush = true
            })
            {
                string message;

                // 5. Receive messages until client disconnects
                while ((message = reader.ReadLine()) != null)
                {
                    Console.WriteLine("Received: " + message);

                    // 6. Process and respond
                    writer.WriteLine("Server received: " + message);
                }
            }

            Console.WriteLine("Client disconnected.");
        }
    }
}
```

**Understand these important lines:**

| C# code | Meaning |
|---|---|
| `TcpListener` | Creates the TCP server listener |
| `IPAddress.Any` | Listens on available local network interfaces |
| `server.Start()` | Starts listening |
| `AcceptTcpClient()` | Waits for and accepts a client |
| `GetStream()` | Gets the communication stream |
| `ReadLine()` | Reads one newline-terminated message |
| `WriteLine()` | Sends a newline-terminated response |

**Limitation of this basic example:** It handles clients sequentially. For multiple simultaneous clients, accept each connection and handle it independently (for example, with async tasks). A production server also needs timeouts, error handling, resource limits and a defined message protocol.

# 5. Generic C# example — simple TCP client

```csharp
using System;
using System.IO;
using System.Net.Sockets;

class TcpClientApp
{
    static void Main()
    {
        // 1. Create TCP client
        using (TcpClient client = new TcpClient())
        {
            // 2. Connect to server
            client.Connect("127.0.0.1", 5000);

            Console.WriteLine("Connected to server!");

            // 3. Get communication stream
            using (NetworkStream stream = client.GetStream())
            using (StreamReader reader = new StreamReader(stream))
            using (StreamWriter writer = new StreamWriter(stream)
            {
                AutoFlush = true
            })
            {
                // 4. Send message
                writer.WriteLine("Hello Server");

                // 5. Receive response
                string response = reader.ReadLine();

                Console.WriteLine("Server response: " + response);
            }
        }

        // 6. Connection is closed when disposed
    }
}
```

Run the server first, then run the client. The client connects to `127.0.0.1:5000` (the same computer, port 5000), sends a line and displays the server's response.

# 6. How to explain multiple clients

An interviewer may ask:

**"What if 100 clients connect to your server at the same time?"**

Answer:

"The server should not process one client's entire communication loop on the main accept thread. I would keep the accept loop running and create a separate asynchronous task or worker for each accepted client connection. Each client gets its own socket and connection context. This allows the server to accept new clients while existing clients are communicating."

```text
                   TCP SERVER
                       |
                 Accept Client
                       |
          +------------+------------+
          |            |            |
          v            v            v
      Client 1      Client 2      Client 3
          |            |            |
      Handler 1    Handler 2    Handler 3
          |            |            |
      Socket 1     Socket 2     Socket 3
```

For a real system, limit the number of active connections and tasks; use bounded queues/backpressure where needed.

# 7. Important TCP concept: TCP sends bytes, not ready-made messages

This is a very common interview question.

TCP is a **byte stream**. It does not promise that one send call on the client will correspond to one receive call on the server.

For example, the client sends:

```text
HELLO
```

The server might receive it as:

```text
HE + LLO
```

Or multiple messages could arrive together:

```text
HELLO
HOW ARE YOU
```

Therefore, the application must define how to identify message boundaries. Common approaches include:

1. **Delimiter-based:** for example, newline-terminated messages. The C# example above uses this.
2. **Length-prefixed:** a header contains the message length, followed by that many body bytes.
3. **Fixed-size messages:** every message has a known size.

For the Client Dispatcher, the screenshots describe a fixed packet header containing a Message Length field. The actual field size, offsets and byte order must be checked in the source code.

# 9. Interview questions and short answers

### Q1. What is TCP?

TCP is a connection-oriented transport protocol. It provides reliable, ordered delivery of a byte stream between two endpoints.

### Q2. What is the difference between TCP client and TCP server?

The server listens on an IP/port and accepts connections. The client initiates a connection to the server.

### Q3. What is a socket?

A socket is a communication endpoint used by an application to send and receive data over a network.

### Q4. What is the difference between IP address and port?

An IP address identifies the network endpoint/machine. A port identifies the application endpoint on that machine.

### Q5. How does a server handle multiple clients?

It accepts connections continuously and handles each accepted client independently, commonly using asynchronous I/O or worker tasks.

### Q6. Does one `Receive()` always return one complete message?

No. TCP is a byte stream. The application needs framing, such as a delimiter or a length-prefixed header.

### Q7. How do you know a client disconnected?

A zero-byte read from a TCP stream indicates that the peer has gracefully closed its sending side. Socket exceptions or failed I/O can indicate other connection failures.

### Q8. What happens if the server is not running?

The client cannot establish the connection. It should handle the connection exception and, if appropriate, retry using a controlled retry policy.

### Q9. Can client and server send data at the same time?

Yes. TCP supports two-way communication. Both endpoints can send and receive data over the same connection.

### Q10. How do you send a response to the correct client?

Maintain the connection/socket associated with that client and use that connection when sending the response. In the CD notes, `TerminalCollection` tracks terminal sockets by Terminal ID.

# 10. Best interview answer — explain your approach

If the interviewer says:

**"Build a TCP/IP Client-Server application. How will you approach it?"**

You can say:

"I would divide the application into two parts: TCP Server and TCP Client.

First, on the server side, I would create a TCP listener, configure its IP address and port, and start listening for incoming connections.

On the client side, I would create a TCP client and connect to the server using its IP address and port.

Once the connection is established, the server accepts the client and obtains a socket. Both sides can then communicate using the TCP stream.

The client sends a message, the server receives it, processes it and sends a response back through the same connection.

I would keep the connection open if multiple messages need to be exchanged. For multiple clients, I would handle each accepted connection independently using asynchronous processing.

I would also define a message-framing protocol because TCP provides a byte stream, not individual application messages. Finally, I would handle disconnections, exceptions and resource cleanup properly.

In our Client Dispatcher project, we extend this basic concept by maintaining terminal connections in `TerminalCollection`, validating packet headers, checking login state and routing messages based on their message codes."
